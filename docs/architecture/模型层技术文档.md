## 1. 模型层定位与分层架构

模型层是 LearnAgent 的 **AI 能力引擎**：接收后端（Spring Boot）的内部 HTTP 调用，完成"意图识别 → 规划 → 检索 → 多专家推理 → 校验 → 报告生成"的完整推理链路，并把推理过程以 SSE 事件流实时送达前端审计。

模型层内部按职责分为六层：

| 层 | 职责 | 关键模块 |
|:---|:---|:---|
| **接入层** | HTTP/SSE 路由与内部 JWT 鉴权 | `app/main.py`、`app/routers/*`（stream/code/medical/profile/evaluation/admin）、`app/runtime.py` |
| **治理层** | 推理并发上限、任务注册表、SSE 帧编码与心跳 | `app/utils/concurrency.py`、`app/utils/task_manager.py`、`app/utils/sse.py` |
| **编排层** | LangGraph 状态图、Planner/Executor/RePlan、监督者 | `app/agents/orchestrators/*`（clinical_graph/learning_agent/supervisor + nodes/*） |
| **能力层** | 9 位专家、Hybrid RAG、共享记忆、医学多模态、代码沙箱 | `app/agents/assistant.py`、`app/rag/*`、`app/agents/core/shared_memory.py`、`app/services/*` |
| **运行时** | 全局资源字典、线程池、任务生命周期 | `app/runtime.py`、`app/utils/task_manager.py` |
| **配置** | YAML 配置热加载、专家/规则/提示词/报告模板 | `app/config/*`（config_loader + 5 个 yaml + qwen.py） |

**依赖方向**：`接入层 → 治理层 → 编排层 → 能力层 → 外部模型（DashScope Qwen 系列）`，配置层被所有层引用。

# runtime.py —— 双算法兼容

# HS512 仅用于兼容升级窗口期的历史令牌，新令牌统一 HS256

## 4. 治理层：并发控制与 SSE 流式协议

### 4.1 推理并发治理（InferenceSlot 信号量）

外部模型（DashScope）有 QPS/并发配额，模型层用**进程级 asyncio 信号量**限制并发推理数：

```python
# utils/concurrency.py
MAX_CONCURRENT_TASKS = int(os.getenv("MAX_CONCURRENT_TASKS", "10"))   # 默认 10
INFERENCE_SLOT_TIMEOUT = float(os.getenv("INFERENCE_SLOT_TIMEOUT", "5"))

class InferenceSlot:
    async def __aenter__(self):
        try:
            await asyncio.wait_for(_semaphore.acquire(), timeout=self._timeout)
        except (asyncio.TimeoutError, TimeoutError):
            raise TimeoutError(f"模型服务繁忙：并发推理已达上限 {MAX_CONCURRENT_TASKS}，请稍后重试")
        self._acquired = True
        return self

    async def __aexit__(self, *exc_info):
        if self._acquired:
            _semaphore.release()
```

路由层获取槽位失败时转 HTTP **503**：

```python
# routers/stream.py
slot = InferenceSlot()
try:
    await slot.__aenter__()
except TimeoutError as exc:
    raise HTTPException(status_code=503, detail=str(exc))
```

### 4.2 任务注册表（AsyncTaskManager）

`/model/get_result` 用 `asyncio.create_task` **无界启动后台推理**，结果事件写入进程内任务注册表（`TaskInfo.events` 列表 + `asyncio.Event`），SSE 端以 `wait_for_new_event(index, timeout)` **增量读取**。`MAX_TASKS=500`、`MAX_AGE_SECONDS=24h` 惰性清理——这就是"断点续流"（`last_event_index`）能力的来源。

### 4.3 自实现 SSE 组件（EventSourceResponse）

替代已归档的 `sse-starlette`，序列化约定与其 3.x 一致：

```python
# utils/sse.py —— 帧编码
def encode_event(data: Any) -> bytes:
    if isinstance(data, dict) and (_SSE_CONTROL_KEYS & set(data.keys())):
        return _encode_named_event(data)          # 命名事件：comment/id/event/retry/data 顺序
    if isinstance(data, dict):
        text = json.dumps(data, ensure_ascii=False, separators=(",", ":"), allow_nan=False)
    else:
        text = str(data)
    lines = [f"data: {chunk}" for chunk in _split_lines(text)]
    return (_SEP.join(lines) + _SEP + _SEP).encode("utf-8")   # \r\n 分隔 + 结尾双空行
```

**心跳机制**：路由统一 `EventSourceResponse(guarded_stream(), ping=15)`，上游 15 秒无输出时自动插入注释帧 `: ping`，防止反向代理/连接空闲超时误杀长推理流。实现上用"独立生产者任务 + `asyncio.Queue`"解耦，超时只取消队列接收、**不会**把 `CancelledError` 传播进上游生成器导致流截断。

### 4.4 统一推理入口调用链

```
POST /model/get_result
  → verify_token()
  → resources.get("model")（未就绪 → 503）
  → InferenceSlot 占槽（超时 → 503）
  → asyncio.create_task(run_agent_background(...))   # 后台驱动整条推理链
  → 先发 {"type":"init","taskId":...}
  → EventSourceResponse(stream_task_events(...), ping=15)  # 增量转发任务事件
```

## 5. 编排层：LangGraph 状态图与请求生命周期

### 5.1 状态对象（LearningState）

`app/agents/core/schema.py` 定义 `LearningState(TypedDict)`，是全链路的**共享黑板**，关键字段：

- 输入：`case_text`（问题）、`all_info`（历史摘要）、`report_mode`、`images`、`profile_summary`
- 中间产物：`learning_questions`、`evidence`、`retrieval_sources`、`proposal`、`critique`
- 专家协作：`active_experts`、`expert_advices`、`debate_history`、`arbitration_result`、`agent_messages`（M2 对话）、`blackboard`（M3 黑板）、`convergence`（收敛结论）
- 质量控制：`validation_passed`、`validation_feedback`、`reflection_count`、`agent_weights`（退火权重）、`rejection_categories`
- 规划：`plan`、`plan_rationale`、`plan_results`；监督者：`supervisor_trace`、`supervisor_roles`、`supervisor_reason`
- 记忆：`shared_memory_hits`、`memory_entropy_scores`、`consensus_result`

### 5.2 图结构与条件路由

`clinical_graph.py` 的 `LearningGraphBuilder.build()` 构建（`MemorySaver` 检查点）：

```
                        ┌─────────────────────────────┐
                        ▼                             │
 intent ──┬─ non_stroke/irrelevant → reject → END    │
          ├─ knowledge → knowledge_answer → END      │
          ├─ code_assist → generate_report → END     │
          ├─ tutor(+supervisor) → supervisor → END   │
          └─ profile/resource/assessment/... ─┐      │
              │ 有影像: analysis → vision →(相关) planner   │
              │ 无影像: → planner ────────────────┘        │
              planner → execute_plan → validate ─┬─ pass → generate_report → END
                                                  ├─ retry → planner（RePlan，反思上限内）
                                                  └─ fail  → generate_report（强制输出）
```

四条条件边（全部在代码中可回溯）：

| 条件边 | 函数 | 逻辑 |
|:---|:---|:---|
| intent 出口 | `_route_intent` | non_stroke→reject；code_assist→直接报告；knowledge→直答；tutor 且监督者启用→supervisor；其余多步任务→有影像走 analysis 否则 planner |
| analysis 出口 | `_route_after_analysis` | 有影像→vision，否则→planner |
| vision 出口 | `_route_after_vision` | `is_image_stroke_related`→planner，否则→reject_image |
| validate 出口 | `_route_validation` | passed→pass；`reflection_count < max_reflection_count`→retry（回 planner）；否则 fail 强制输出 |

### 5.3 三通道流式与节点事件包装

`learning_agent.py` 用 `graph.astream(initial_state, stream_mode=["custom","updates","messages"])` 三通道消费：

- **custom**：节点中途事件（`_with_node_events` 包装器在进入每个节点时经 `get_stream_writer()` 发 `node_start`；子节点再发 `thinking/experts_selected/expert_done/debate/proposal/agent_msg/blackboard`）
- **updates**：节点完成输出（`node_done` + `token/replace` 报告文本；supervisor 节点在此补发点将 `experts` 事件）
- **messages**：LLM token 级流（仅 `generate_report`/`knowledge_answer` 两个流式节点）

```python
# clinical_graph.py —— 节点进入即发 node_start 自定义事件
def _with_node_events(name: str, fn):
    async def wrapper(state, **kwargs):
        from langgraph.config import get_stream_writer
        writer = get_stream_writer()
        writer({"type": "node_start", "node": name})   # ← 前端节点标签的数据源
        return await fn(state, **kwargs)
    return wrapper
```

节点名到前端标签的翻译表（`_NODE_LABELS`）：

```python

## 6. Planner 结构化规划与 RePlan 反思循环

### 6.1 计划数据契约（schemas/plan.py）

步骤类型被**严格限制在白名单**内，LLM 无法幻觉出越界动作：

```python
# 步骤类型白名单：每种类型对应 ExecutorNode 中的一个既有能力
PLAN_STEP_TYPES = ("analyze", "retrieve", "expert_reason", "finalize")
MAX_PLAN_STEPS = 6

class PlanStep(BaseModel):
    step_type: STEP_TYPE_LITERAL      # analyze | retrieve | expert_reason | finalize
    title: str                        # 前端 SSE 展示标题
    goal: str = ""
    depends_on: List[int] = []        # 依赖的前置步骤序号（0-based）

class ExecutionPlan(BaseModel):
    steps: List[PlanStep]             # 1~6 步
    rationale: str = ""               # 规划理由（审计展示）
```

### 6.2 归一化防御（normalize_plan）

LLM 输出计划后强制修正：过滤白名单外步骤 → 清除越界/自依赖 → 只保留最后一个 `finalize` 之前的内容 → 缺失 `finalize` 自动补齐 → **缺少 `expert_reason`（内容生产步骤）自动插入**（不变量：报告节点消费 expert_reason 产出的 proposal，缺了会生成空报告）。

### 6.3 三级降级

1. **结构化输出**（pydantic 约束生成）；
2. 失败 → **JSON 解析**（`JsonParser`）；
3. 仍失败 → **默认计划** `build_default_plan()`，等价于升级前的固定管线：

```python
def build_default_plan(intent_type: str = "") -> ExecutionPlan:
    return ExecutionPlan(
        steps=[
            PlanStep(step_type="analyze",        title="分析学习需求", ...),
            PlanStep(step_type="retrieve",       title="检索循证资料", ...),
            PlanStep(step_type="expert_reason",  title="多专家推理与辩论", ...),
            PlanStep(step_type="finalize",       title="汇总生成最终报告", ...),
        ],
        rationale="默认计划（规划器不可用时的兜底，与升级前固定管线一致）",
    )
```

### 6.4 RePlan 循环

`validate` 节点判定不合格且反思次数未达上限（`max_reflection_count: 1`，rules_config.yaml）时，`_route_validation` 返回 `retry`，**反馈随 state 回到 `planner` 重新规划**：

```python
# clinical_graph.py
if state['validation_passed']:
    route_decision = "pass"
elif state['reflection_count'] < self.max_reflection_count:
    route_decision = "retry"      # → planner（退火权重已更新）
else:
    route_decision = "fail"       # 强制输出，避免无限循环
```

**示例**：一次包含 `expert_reason` 步骤的生成计划，其 `node_done` 摘要形如：

```
规划完成（3 步：需求分析、多专家推理与辩论、汇总生成最终报告）
```

## 7. 多专家并行、会诊对话与辩论仲裁

### 7.1 选人三级优先（ReasonNode._resolve_active_experts）

1. **监督者显式点将**（`state.active_experts_override`，须落在专家白名单内，否则回退规则编排）；
2. **意图 + 难度规则动态编排**（`expert_config.yaml` 的 `intent_expert_mapping` 按意图过滤 + 每位专家 `min_difficulty` 门槛，结果为空时取前 3 位）：
   - 例如 `resource` 意图默认召集：需求分析、文档撰写、题目生成、质量审核、学习激励 5 位；
   - **仲裁自动介入**：`debate_enabled` 且仲裁不在名单中时，若 `difficulty_score >= 0.6` 则追加仲裁智能体（对应其 `min_difficulty: 0.6`）；
3. 动态编排关闭时回退：全员参与。

选人结果第一时间流式送达前端（可审计）：

```python
# reason_node.py —— 点将事件
_emit({
    "type": "experts_selected",
    "node": "reason",
    "active_experts": list(active_experts),
    "reason": (
        "监督者显式点将" if state.get("active_experts_override")
        else f"意图+难度规则编排（难度 {state.get('difficulty_score', 0.5):.2f}）"
    ),
})
```

### 7.2 并行专家推理

```python
# reason_node.py —— 每位专家一个独立推理任务
tasks = []
for expert in self.experts:
    role = expert.get("role")
    if role not in active_experts:
        continue
    weight = agent_weights.get(role, 1.0)   # 退火权重影响采样
    tasks.append(self._ask_expert(role, instruction, case_info, weight))
# ... asyncio.gather 并发执行，每位专家完成即发 expert_done 事件
```

每位专家发言以 `thinking` 事件流式输出（`专家发言 2/3：画像对话智能体`），供前端逐条展示。

### 7.3 M2 专家间对话 + M3 会诊黑板（DialogueOrchestrator，优先）

`dialogue_enabled: true`、`dialogue_max_rounds: 2`。专家间通过**结构化消息**（`agent_msg` 事件）定向交流，六种 kind：

```yaml
# expert_config.yaml
- {"kind":"question","to":"某专家","content":"向该专家提问的问题"}
- {"kind":"object","to":"某专家","content":"指出对方观点的问题并给出证据"}
- {"kind":"reply","to":"某专家","content":"回答对方对你的提问"}
- {"kind":"agree","to":"某专家","content":"表示认同并补充"}
- {"kind":"revise","to":"__all__","content":"基于讨论修正你的最终意见"}
- {"kind":"finding","to":"__all__","content":"补充一条你认为重要的新发现"}
```

黑板（`blackboard` 事件）承载各专家最终发现，满足条件**提前收敛**（共识已达成则不再继续轮次），收敛结论经 `convergence` 字段下发。

### 7.4 辩论与仲裁（DebateOrchestrator，回退路径）

`debate.enabled: true`、`max_rounds: 1`。辩论记录 + 仲裁裁决经 `debate` 事件流式下发。仲裁由 `llm_synthesis` 依据证据链裁决，输出格式：

```
### ARBITRATION ###    ← 最终裁决结论
### REASONING ###      ← 裁决推理过程
```

### 7.5 综合提案与风险批判

教学总监（`llm_synthesis`）统筹全部专家意见，输出 Proposal + Critique：

```python
synthesis.prompt_template = """

## 9. 能力层 · Hybrid RAG 三阶漏斗检索

### 9.1 三阶漏斗（retrievers.py）

```python
CONFIG = {
    "top_k_per_store": 4,   # 多库模式下每库候选数
    "recall_k": 20,         # 第一阶宽召回：向量/BM25 各召回 20 篇
    "rrf_top_k": 20,        # 第二阶粗排：RRF 融合后取 20 篇
    "top_k_final": 3,       # 第三阶精排：最终喂给 LLM 的 3 篇
}
```

```
第一阶（宽召回）   向量检索 + BM25 并行召回 40 篇候选
第二阶（粗排）     RRF 倒数排名融合 → 20 篇（零外部 API 开销）
第三阶（精排）     Qwen Reranker 深度语义精排 → 3 篇喂给 LLM
```

**设计收益（代码注释原话）**："Reranker 只需处理 20 篇而非 40 篇，节省 API 开销；精排结果质量远高于纯 RRF 或纯 Reranker。"

### 9.2 自实现 BM25（CJK 二元组分词）

`rag/bm25.py` 的 `BM25Retriever`：**分词器自实现**（CJK 文本按重叠二元组 bigram + ASCII 整词小写），底层打分用 `rank_bm25.BM25Okapi`（k1/b 未显式配置，为库默认值）；检索时做词项重叠过滤 + `[:k]` 截取，默认 `k=4`，HybridRetriever 引擎内覆盖为 `recall_k=20`。向量检索失败时 BM25 是主降级路径（不依赖外部 API）。

### 9.3 RRF 融合（fusion.py）

完全不看原始相似度分数，只看排名，避开 Dense 向量与 BM25 分值的量纲差异：

```python
def reciprocal_rank_fusion(vector_results, bm25_results, k=60, top_k=5):
    # RRF_Score(d) = 1/(k + Rank_Dense(d)) + 1/(k + Rank_BM25(d))
    rrf_scores[content] = (1.0 / (k + d_rank)) + (1.0 / (k + s_rank))
    # 未在某一列表中出现的文档给予默认排名 len(list)+1
```

### 9.4 精排与医学评分兜底

- 首选 **Qwen Reranker**（`qwen3-rerank`，top_n 精排）；
- 调用失败时**不回退为原始 embedding 顺序**，而是 `MedicalEvidenceReranker.fallback_rerank`（RRF 归一化 + 医学评分因子兜底）；
- **医学评分权重**（scoring.py）：semantic 0.35 / evidence_type 0.25 / authority 0.20 / recency 0.10 / topic 0.10，干预内容 +0.15 加分、不相关内容 -0.5 淘汰惩罚；
- 多 collection 场景（`MultiCollectionSearchEngine`）：**5 个隔离 collection**（按证据类型分库），每个 collection 一个 Chroma + BM25，先库内混合检索 → 跨库统一 RRF → **Mismatch Filter**（消除跨库不一致候选）→ 医学评分重排。

### 9.5 降级容错与缓存

| 故障 | 降级路径 |
|:---|:---|
| Qwen 向量检索失败 | 继续使用 BM25 |
| BM25 失败 | 返回已得结果 |
| Rerank 失败 | RRF 归一化 + 医学评分兜底 |
| 查询缓存 | `MD5(query + top_k)` 内存缓存，TTL 300 秒，不跨进程 |

```python
# retrievers.py —— 缓存键（多库模式下还拼接 evidence_type 与决策节点）
cache_key = hashlib.md5(
    f"{query}_{top_k_final}_{evidence_type or ''}_{(decision_nodes or [])}".encode("utf-8")
).hexdigest()
```

### 9.6 检索服务对外接口

`EvidenceRetrievalService.aparallel_retrieve(sub_questions)` 对多个子问题**异步并行检索**，证据以文本形式拼接（`---` 分隔），`RetrieveNode` 的 `node_done` 摘要统计片段数：`检索到 {count} 个参考片段`。RAG 依据（指南/页码）经 `retrieval_sources` 进 `node_done` 事件的 `sources` 字段，前端"AI 推理与检索依据"面板展示。

## 10. 能力层 · 三层闭环共享记忆系统

`agents/core/shared_memory.py` 实现三层解耦架构，解决**跨会话状态冲突**与**低价值信息污染**问题。

### 10.1 物理层：SharedMemoryStore（ChromaDB 向量存储）

- `PersistentClient` + cosine 空间，持久目录 `chroma_db_shared_memory`；
- **三级降级容错**：
  1. 初始化失败 → `_initialized=False` 静默降级（记忆功能不可用时不影响主链路）；
  2. 写入失败 → `_ef` 包装器自动重试生成向量，dimension 冲突不可恢复（判死）；
  3. 检索失败 → 降级 `query_texts` 关键词检索（relevance 固定 0.5）。
- **记忆条目结构**：id 格式 `mem_{agent}_{毫秒时间戳}`；metadata 字段 `source_agent` / `timestamp` / `entropy_score` / `knowledge_points` / `confidence`（默认 0.8）/ `intent_type` / `session_id` 及调用方透传字段。

### 10.2 逻辑层：ConsensusEngine（信誉加权投票共识）

```python
# 冲突判定：Jaccard 重叠度 < 0.4 视为冲突（conflict_threshold）
# 共识达成：combined = 信誉 × 会话权重 归一化后，top ≥ 0.6（min_agreement_ratio）
# 信誉更新：score = correct / total，写入 data/agent_reputation.json
```

跨会话对新旧记忆冲突时，按各智能体的**历史信誉**加权投票消解，信誉数据持久化到 `data/agent_reputation.json`。

### 10.3 元记忆过滤层：MetaMemoryFilter（四维信息熵）

```python
# 四维熵评分（shared_memory_config.yaml 权重）
entropy_score = (
    0.2 * shannon_score +   # Shannon 熵
    0.3 * (1 - keyword_score) +   # 关键词覆盖率
    0.3 * (1 - density_score) +   # Token 密度
    0.2 * (1 - length_score)      # 长度
)
# 阈值 0.85：熵分 < 0.85（低熵、高信息量）才触发持久化
```

- `min_length: 20`（过短内容不评估）；
- `force` 参数可跳过过滤强制存储（注意：`store_insight` 的 force 未透传，仅底层 `SharedMemoryStore.store` 生效）；
- 持久化策略：`auto_store_high_value: true`、`min_confidence: 0.7`、每会话最多 10 条记忆。

### 10.4 读-写-信誉反馈闭环

```
写：问答结果 → 四维熵过滤（低熵才写入，force 可跳过）→ ChromaDB 持久化
读：检索 → relevance = 1 - distance → 与检索证据融合喂给专家
反馈：校验结果 → update_reputation_from_validation（失败时记入信誉最低的 len//3 名智能体）→ 信誉回灌投票权重
```

`SharedMemorySystem` 对外的五个公开方法：`store_insight` / `retrieve_relevant` / `resolve_conflict` / `update_reputation` / `get_enhanced_weights`（注意：`store_insight` 的 `force` 参数未透传，仅底层 `SharedMemoryStore.store` 层生效）。

### 10.5 上下文摘要（utils/context_summary.py）

`update_all_info(previous, question, answer, threshold=2000)`：

```python
current_len = len(previous_all_info) + len(question) + len(answer)
is_triggered = current_len > 2000          # 滑动窗口
if is_triggered:
    updated = self.summarize_context(...)   # LLM 合并摘要
else:
    new_turn = f"问：{question.strip()}\n答：{answer.strip()}"   # 直连追加
# 同时复用 MetaMemoryFilter.compute_entropy_score(answer) 记录答案熵值
```

## 11. 能力层 · 医学多模态与输入守卫

### 11.1 输入守卫（IntentNode，第一道防线）

`intent_node.py` 融合**确定性规则 + 领域证据 + LLM 辅助判断**：

- **业务模式规则**：`_MODE_INPUT_RULES` 把 22 个 report_mode 映射为 `InputRule(intent, name, scope, require_stroke)`（scope 为允许范围文案）；
- **领域证据**：`_MODE_EVIDENCE_GROUPS` 每模式定义关键词组，`all(any)` 要求每组至少命中一个；tutor 有非空文本即通过；
- **医学红线**：`require_stroke=True` 且无图片时，`_STROKE_KEYWORDS`（**80+ 个卒中关键词**：脑卒中/脑梗/溶栓/NIHSS/rtPA/ASPECTS/FAST 等）必须命中，否则拒绝；
- **代码请求放宽边界**：`code_assist` 的 `InputRule` 为 `require_stroke=False`，且正则 `(?:\bdef\b|\bclass\b|\bimport\b|[(){}\[\]=;/])` 识别到代码特征、确定性校验通过后**直接跳过 LLM 输入守卫**（防止真实代码请求被误拦截，对应测试 `test_intent_input_guard.py`）；
- **LLM 辅助宽准入**：守卫链输出 `{is_function_related, is_stroke_related, reason}`，把"任务类型/辅助类型/资源格式要求"等包装字段视为系统元数据、不可仅凭其判定相关；意图分类输出 `type + difficulty_score + is_stroke_related`；
- **自由输入路径**：无图且无关键词 → `non_stroke`；有图但文本无关键词 → `knowledge` + `_image_pending_check: True` **放行给 vision 节点终判**；关键词命中但 LLM 判不相关 → 以关键词为准放行；
- 意图枚举：`profile / resource / tutor / assessment / learning_path / knowledge / irrelevant`（`non_stroke` 是内部拒绝标记）；意图关键词表在 `limits_config.yaml`。

### 11.2 医学影像门控（VisionNode，第二道防线）

- **Tier 0 预校验**：MIME 白名单（jpeg/png/jpg/bmp/tiff/dicom 等 7 种），显式拒绝 `text/`、`application/pdf`、`application/zip`、`application/json`、`video/`、`audio/`；格式/大小（单张 ≤14MB）/数量（≤5 张）不达标直接拒绝；
- **Tier 1 门控**：AI 判断影像是否与脑卒中相关；
- **Tier 2/3 内容检测**：术语计数等硬规则（医学术语 ≥5 直接放行）；
- **放行策略**：仅检查前 3 张图，**一张通过即放行、全否才拦截**；
- 拦截时按层级给出不同文案（`reject_image` 节点的 `_gate_result` 分支：预检未通过 / 对抗性提示检测 / 图片已被拦截 / 内容与脑卒中无关）。

### 11.3 医学影像分析（MedicalVisionService）

- Qwen VL 结构化分析：**影像类型按优先级分类**（angiography > ct > mri > pathology > ecg > lab_report > radiology > clinical_photo > illustration > courseware），每类有专属系统 Prompt（如神经影像四步判读 + "禁止给出确定性的临床诊断结论"）；
- 输出 schema（`schemas/medical_image.py`）：`image_type / anatomical_region / key_findings / abnormalities / normal_structures / differential_diagnosis / recommended_confirmatory_tests / urgency_level / confidence / limitations / raw_description`；
- JSON 解析三策略容错（整体 JSON / ```json 代码块 / 最外层 {}），失败回退原始文本前 500 字、confidence 0.3；
- 单图分析 / 多图对比（≥2 张，comparison_mode=progression/comparison）/ 病例流式分析（`/model/medical/analyze-case` 走 tutor 报告链路）；
- **Vision-RAG 桥接**（`VisionRAGBridge`）：影像发现转检索查询（top_k=3），从本地知识库取循证片段，实现"影像-指南"交叉印证。

### 11.4 OCR 与 DICOM（受控失败）

- OCR：检验报告（`LabReport`，含 `abnormality_direction: high/low/critical_high/critical_low`）/ 处方（`PrescriptionInfo`：药名/剂量/频次/途径/疗程/备注）/ 通用医学文本，结构化提取；Prompt 要求"不提取患者身份信息"、识别不清标"识别不清"；
- DICOM：元数据解析（`pydicom.dcmread`，只提取技术参数、`has_phi_stripped=True` 不取 PHI）、`dicom-to-png` 预览转换（默认**脑窗 WW=80 / WL=40**，clip→uint8→PNG→data URI）；
- **依赖缺失（pydicom/Pillow）时返回受控空结果而非抛异常**（`DICOMMetadata(has_phi_stripped=True)`、`dicom_to_png_base64` 返回 None）。

### 11.5 代码沙箱（code_sandbox.py）

`run_python(code, input_data, timeout=30)`：

- 空代码 / 超长（`MAX_CODE_CHARS=50000`）快速失败；超时夹在 1~60s；
- 独立临时目录 + `subprocess.run([sys.executable, "-I", script_path], ...)`（`-I` 隔离模式忽略 PYTHONPATH/site-packages）；
- 资源限制：`RLIMIT_CPU 60s / RLIMIT_FSIZE 8MB / RLIMIT_AS 1GB / RLIMIT_NPROC 512`（macOS 降级）；
- 输出截断 `MAX_OUTPUT_CHARS=64000`；返回 `ExecutionResult(success/stdout/stderr/exit_code/execution_time/truncated/error)`；
- 注释明确：进程隔离只是第一道防线，生产依赖 Docker（model/Dockerfile）。

## 12. 能力层 · 双层校验与有界反思

`validate_node.py` 实现**规则引擎硬拦截 + LLM 反思软审查**双层校验：

```
规则引擎（硬）   contraindication_rules 按功能分类（资源生成/画像构建/学习路径）
                → 命中即驳回，rejection_categories 记录分类
LLM 反思（软）   enable_llm_reflection=true 时 LLM 输出质量评分与驳回原因
                → 驳回原因随 state 带回 ReasonNode 反思模式
退火策略         驳回后按 rejection_category 分类（factual_error / logical_contradiction /
                personalization_insufficient / medical_inaccuracy / completeness_issue），
                按 weight_decay_factor=0.5 衰减所有参与专家权重（下限 0.2），
                并在 prompt 追加【退火修正指引】；驳回反馈经 validation_feedback
                带回 planner（重新规划）与 ReasonNode（反思模式 _build_correction_hint）
```

```yaml
# rules_config.yaml
validation_settings:
  max_reflection_count: 1      # RePlan 循环上限（有界反思，防死循环）
  enable_rule_engine: true
  enable_llm_reflection: true
annealing:
  enabled: true
  weight_decay_factor: 0.5
```

校验失败且反思次数未达上限 → `retry` 回 `planner` 重新规划（§6.4）；达到上限 → `fail` 强制输出（优雅降级，绝不让用户空等）。

| vision | qwen-vl-max | 医学影像 | — |

`QWEN_FORCE_TURBO=true` 时所有对话档位统一使用 qwen-turbo（省成本/提速）。

## 14. SSE 事件协议总表

| 事件 | 含义 | 主要发出方 |
|:---|:---|:---|
| `init` | 新任务开始（携带 taskId） | stream 路由 |
| `meta` | 任务元信息 | stream 路由 |
| `node_start` | 节点进入标签 | clinical_graph（`_with_node_events`） |
| `thinking` | 推理链中途事件（阶段、专家发言、提案批判） | learning_agent / 各节点 |
| `node_done` | 节点完成摘要（含 RAG 依据 sources） | learning_agent |
| `experts` | 参与专家名单 + 各专家完整发言 + **选人理由** | learning_agent（reason/supervisor） |
| `debate` | 多专家辩论记录 + 仲裁裁决 | learning_agent |
| `agent_msg` | M2 专家间定向对话（from/to/round/kind/content） | learning_agent |
| `blackboard` | M3 会诊黑板（发现 + 收敛结论 + 仲裁） | learning_agent |
| `token` | 最终报告逐字流 | learning_agent |
| `replace` | 完整报告替换（清空此前 token 累计） | learning_agent |
| `done` | 流结束（画像模式携带 `profile_dimensions`） | agent_runner |
| `error` | 结构化错误（含错误码） | agent_runner |

> 内部自定义事件（不直接下发前端）：`experts_selected`（点将名单先行）、`expert_done`（每位专家完成）、`proposal`（提案+批判）——由 learning_agent 翻译为 `experts/thinking` 对外事件。

## 15. 端到端示例：一次完整请求的事件流

以"学习画像构建"（report_mode=`profile_build`）为例，用户问：**"我是一名大二医学生，基础一般，想系统学习脑卒中"**：

```
POST /model/get_result {question, report_mode: "profile_build"}
  → verify_token → InferenceSlot 占槽 → create_task(run_agent_background)

SSE 事件流（前端按到达顺序展示）：
─────────────────────────────────────────────────────────────
event: init        {"newTalk":true, "talkId":"2090297...", "type":"init"}
event: meta        {"originalType":"init", "type":"meta", "taskId":"22f30dc6..."}
event: thinking    {"step":"intent", "title":"正在判断问题类型..."}
event: node_done   {"node":"intent", "content":"已将本次请求识别为：profile。"}
event: thinking    {"step":"planner", "title":"正在规划任务步骤..."}
event: node_done   {"node":"planner", "summary":"规划完成（3 步：需求分析、多专家推理与辩论、汇总生成最终报告）"}
event: thinking    {"step":"execute_plan", "title":"执行步骤 1/3：需求分析"}
event: thinking    {"step":"execute_plan", "title":"执行步骤 2/3：多专家推理与辩论"}
event: experts     {"selection_reason":"意图+难度规则编排（难度 0.50）",
                    "active_experts":["画像对话智能体","特征抽取智能体","学习激励智能体"]}
event: thinking    {"title":"专家发言 1/3：特征抽取智能体", "content":"**结构化学习特征抽取结果：** ..."}
event: thinking    {"title":"专家发言 2/3：画像对话智能体", "content":"好的，感谢你的介绍！..."}
event: thinking    {"title":"专家发言 3/3：学习激励智能体", "content":"...（学习计划表与激励建议）"}
: heartbeat                                        ← 空闲心跳（每 15s）
event: agent_msg   {"from":"画像对话智能体","to":"特征抽取智能体","kind":"question","content":"你提到...是否有依据？"}
event: blackboard  {"entries":[...], "convergence":"共识已达成", "arbitration":"以证据为准"}
event: node_done   {"node":"reason", "summary":"多智能体推理完成 (3 位专家)"}
event: node_done   {"node":"validate", "summary":"质量校验完成"}   ← 校验通过 → pass
event: node_done   {"node":"generate_report", "summary":"生成报告，长度: 1506 字符"}

event: done        {"profile_dimensions":{8 维画像}, "name":"脑卒中基础知识"}
: close
─────────────────────────────────────────────────────────────
```
