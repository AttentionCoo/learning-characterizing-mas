# 架构选型说明：为什么这两个项目一个"工作流"，一个"多 Agent"

> 本文回答一个问题：**同一位作者，为什么临床决策项目（`stroke-multi-agent-system`）做成"骨架固定的工作流 + 局部 Agent"，而教育个性化项目（`learning-multi-agent-system`，即本仓库）做成"监督者主路由 + 专家注册表"？**
>
> 结论先说：**两者不是先进与落后的关系，而是风险长在不同维度导致的两种正确解。** 项目 A 的风险长在**时序**（漏步、乱序、跳安全闸口），所以用**图的边**保证；项目 B 的风险长在**权柄**（谁有权断言学生属性、凭什么证据、谁有权写画像），所以用**角色边界与能力面**保证。

---

## 0. 一条统一法则

两个项目在做**同一件事**：

> 把「**不可协商的约束**」放到模型够不着的地方，把「**不可穷举的选择**」放到模型手里。

区别只在两处：约束长在哪一维、选择空间有多大。

| | 项目 A `stroke-multi-agent-system` | 项目 B `learning-multi-agent-system`（本仓库） |
|---|---|---|
| 领域 | 脑卒中临床决策支持（溶栓） | 脑卒中医学教育个性化学习 |
| 编排形态 | 工作流打底 + 局部 Agent | 监督者路由 + 专家注册表 |
| 约束载体 | **图的边**（节点顺序、条件路由、强制闸口） | **角色权柄 + 能力面**（谁能断言/写什么） |
| 放给模型的选择 | 工具选择、检索策略 | 专家调度、教学内容、访谈策略 |
| 一句话 | 骨架固定，关节自由 | 权柄分明，调度可协商 |

## 1. 项目 A：为什么是 workflow 而不是自主 Agent

**代码位置**：`D:\CompetitionProject\stroke-multi-agent-system\model\app\agents\orchestrators\clinical_graph.py`（455 行）

**核心原因一句话**：**医疗场景的失败代价不对称，必须用"结构换确定性"——把"必须发生的事"交给图保证，只把"分支空间大、规则难穷举的事"交给模型自主。**

具体有 7 条现实理由：

### 1.1 硬性安全约束无法靠 Prompt 保证，只能靠图结构

溶栓流程有严格的执行依赖：必须先排除出血/血压达标/无禁忌，才能算 rt-PA 剂量。项目里用两层保证：

- `tool_use` 节点的 **Level 优先级**（评估 → 禁忌 → 剂量），并在提示与工具定义里硬约束 `rtpa_dose_calc` 不得先于 `contraindication_check`；
- `validate` 节点的**规则引擎硬拦截**（如活动性出血直接把答案判 fail），不通过就走 compliance → human_review。

如果路径由模型自主决定，这些"必须做的前置步骤"只能靠 prompt 祈祷模型遵守——一旦跳步，输出的是**看起来专业但危险的错误**。图的边是代码，不会忘。

> **代码实证**（`tool_use_node.py` L47-56）：
> ```
> 【工具调用优先级(Level)】
> Level 1 - 基础评估(最先):stroke 类型判断、NIHSS、LVO 筛查、时间窗、ASPECTS
> Level 2 - 安全核查(其次):contraindication_check(禁忌症)、cha2ds2_vasc/has_bled、swallow_screen
> Level 3 - 治疗计算(最后):rtpa_dose_calc、rtpa_monitoring_checklist、出血转化风险分层
> 3. 按 Level 优先级排序调用,rtpa_dose_calc 不得先于禁忌症检查
> ```

### 1.2 医疗错误不可逆 → 循环必须"有界"而不是"自主"

`query_rewrite` 最多 2 轮、`validate` 反思最多 3 次、`human_review` 驳回最多 2 次（`HITL_MAX_REJECTS`）——全部是常量。这带来两个好处：

- **成本/延迟可静态推导**，急诊场景响应时间可预期（多位专家是 `asyncio.gather` 并行的）；
- 不会出现自主 Agent 常见的**不收敛/挂起/烧 token**。`qwen_agent.py` 里专门做了"无效决策默认驳回"就是防这个。

### 1.3 模型能力现实：用工程补模型短板

当前 4 个角色默认都是 `qwen-turbo`（`models.yaml` L27-39）。弱模型做**开放式自主规划**容易跑偏；但配上确定性骨架 + 结构化输出（`make_structured_runner` 双路径回退）+ **规则兜底**（LLM 没调工具时规则引擎按"偏瘫/失语/发病时长"等临床线索自动补调），可靠性就被拉起来了。这是典型的"用编排换模型能力不足"。

### 1.4 全链路流式思考链要求步骤集合可知

前端要逐节点打字机渲染、思考链与消息索引对齐，依赖固定事件契约：`node_start / node_token / node_done / token / node_stats / ask_doctor / human_review / done / error`。**步骤集合必须预先可知**，前端才能稳定渲染、才谈得上"复制全部思考链"。若路径由模型自发生成，每次步骤不同，SSE 契约和 UI 都无法稳定。

### 1.5 可测试、可回归

离线用例（`model/tests/` 共 250 个测试函数）能对节点行为做断言，前提是**图是确定的、可复现的**。若路径由模型自主决定，回归测试本身就是非确定的，改一个 prompt 无法判断是否破坏了流程——这个项目验证过"大批文件加注释零行为变化"，靠的就是确定性。

### 1.6 责任边界：HITL 必须是强制闸口，不能是"模型自觉"

`checkpoint.py`（AsyncSqliteSaver + `interrupt()` / `Command(resume=...)`）保证**报告生成前必经医生复核**，且驳回意见会写回 `validation_feedback` 重推。这是**图上的硬闸口**；在自主 Agent 形态下，"要不要请人确认"本身就成了模型的自由裁量，追责链条会断。

### 1.7 可追溯与合规审计

每个节点、每次检索（`R{轮}-Q{查询}-E{结果}` 证据编号）、模型/知识库/提示词版本都快照留痕，报告可回溯。这需要**固定的检查点结构**才成立。

### 1.8 补充：代码比这条论证更严的地方

审阅 `clinical_graph.py` 时发现一处**比"骨架固定"更强的保证**，值得单独点出：

```python
graph.add_conditional_edges(
    "validate",
    self._route_validation,
    {
        "pass":  "compliance",  # 通过校验 → 合规审计
        "retry": "reason",      # 未通过 → 重新会诊（反思循环）
        "fail":  "compliance",  # 多次失败 → 强制输出(仍走合规审计)
    }
)
```

**即使反思次数耗尽、校验已经"放弃"，输出依然必须穿过 `compliance` 节点才能到报告。** 也就是说：系统可以承认"我没能把它改对"，但**不可以因此绕过安全审计**。安全闸口的边是无条件的，与状态有多差无关。

这是"用结构换确定性"最纯粹的形态——**降级路径的终点仍然是闸口，而不是出口**。

## 2. 项目 A 里故意留给 Agent 的部分

因为那里分支空间大、规则确实难穷举，交给模型自主反而更好：

- **工具选择**（18 个工具、组合方式多）→ function-calling 自主决定；
- **检索策略**（要不要改写查询、改写成什么）→ Agentic RAG 闭环。

最终形态是 **"骨架固定 + 关节自由"**：骨架（节点顺序、安全闸口、循环上限、人机边界）写死在 `clinical_graph.py`，关节（选哪个工具、要不要重查）交给 LLM。

这也正是 LangGraph 官方对 high-stakes / 合规场景的推荐姿势——workflow 编排打底 + 局部 agent 增强。

## 3. 项目 B：为什么必须是多 Agent

**代码位置**：本仓库 `model/app/agents/orchestrators/supervisor.py`、`model/app/agents/registry.py`、`model/app/config/expert_config.yaml`

**核心原因一句话**：**不是为了答案更聪明，而是因为产品需求是「可审计」——关于学生的每条断言必须可回溯证据，生成的教学材料必须过独立审核。这个需求在结构上就是多 Agent 需求：它要求的角色，目标函数天然冲突，塞不进一个 context。**

### 3.1 先排除一个错误答案：不是为了"更聪明"

`AgentRegistry` 接收的是**同一个 `llm` 实例**，10 个专家共用同一个基座模型，差别只有 `system_prompt` 和 `tools` 白名单。所以"10 个专家"绝不等于 10 倍智力。如果产品需求只是"把脑卒中问题答好"，**一个强模型 + RAG 就是正确且更便宜的设计**，多 Agent 在这里是负债。

### 3.2 冲突目标必须分上下文（最根本）

| 角色 | 优化方向 | 与谁冲突 |
|---|---|---|
| 画像访谈 | recall ↑（多问） | ↔ 画像抽取 precision ↑（少写） |
| 画像抽取 | precision ↑（不推断） | ↔ 访谈的挖掘欲 |
| 画像校验 | skepticism ↑（多质疑） | ↔ 抽取的产出量 |
| 文档撰写 | 产出内容 | ↔ 质量审核的否决权 |
| 主张方 | 说服 | ↔ 仲裁的中立 |

「尽可能好奇地挖掘」和「绝不推断任何东西」写进同一个 prompt，会平均成既不敢问也不敢写的温吞输出。分开不是拆任务，是**因为目标函数方向相反**。

### 3.3 写入路径与智能体解耦（最硬）

专家工具面**全是只读**（`model/app/agents/tools.py`）：

| 工具 | 做什么 | 写吗 |
|---|---|---|
| `lookup_evidence` | 在已检索证据里查片段 | 读 |
| `get_student_profile` | 取画像摘要字符串 | 读 |
| `retrieve_shared_memory` | 检索跨会话共享记忆 | 读 |

**10 个专家谁都没有写画像的工具。** 专家输出的是**文本意见**，文本在这个系统里没有通往画像的持久化通道。画像由一条独立管道写入：

```
专家 → 只输出文本（意见/主张）→ 进入 synthesis / debate / report
                                   ↓ （此处没有任何持久化通道）

       ┌─ 另一条独立管道 ────────────────────────────┐
用户输入 → 用户陈述：{case_text}  ← agent_runner.py L126/L164
             ↓  assistant 的报告被明确排除在外
       generate_profile_candidates()   (LLM 抽取成 JSON 候选)
             ↓  _normalize_candidates() 白名单 + 无证据即丢弃
       done_event["profile_update_candidates"]
             ↓  跨语言边界交给后端
       ProfileMergePolicy.shouldApply()  (状态感知合并)
             ↓
       MySQL 落库
```

这是**架构位置隔离**，不是权限分配：不是「9 个发了钥匙、1 个没发」（配置里少写一行 `tools:` 就漏），而是这把钥匙**压根不存在**。对应原则：

> **能力限制（不提供操作）> 指令限制（prompt 里请求）**
> 前者说服不了，后者能被长上下文诱导。

### 3.4 生成者不能当审核者

一个 context 里"写完再自查"必然退化成橡皮图章（自我一致性偏见）。同行评审要分作者和审稿人，是同一个道理。仲裁 prompt 里甚至硬写了「**不要因为多方一致就判定通过——一致性不等于有证据**」——这句指令只有在仲裁者没参与立论时才成立。

在脑卒中场景下，溶栓时间窗写错是**患者安全级错误**，不能靠模型自觉兜住。

### 3.5 可测试 + 失败隔离

每个 Agent 是 `task in → 结构化 report out`，所以 `画像抽取` 能不跑整条流水线就单测（`test_registry.py` / `test_expert_tools.py`）。坏输出落在仲裁点被拦，而不是直接怼到学生脸上。每次工具调用还 emit `agent_tool` 事件，前端可审计"哪个专家调了哪个工具"。

### 3.6 画像写边界：三层防线

| 层 | 机制 | 性质 |
|---|---|---|
| 1 | 专家无写入工具；写入走独立管道、只读用户陈述 | **架构性** |
| 2 | `_normalize_candidates`：维度/字段/来源白名单 + **`evidence` 为空直接丢弃** | 数据校验性 |
| 3 | `ProfileMergePolicy.shouldApply`：`user_statement` 优先、confirmed 不被降级、observed 不被 inferred 降级、置信度/时间戳决胜 | 数据校验性 |

第一层是"LLM 不乱写画像"的根本保证，后两层是纵深防御。

## 4. 对比与推演：为什么两个项目各自是现在这个样子

### 4.1 风险长在哪一维，决定用哪种结构保证

这是两个项目形态差异的**第一性原因**。

| | 项目 A | 项目 B |
|---|---|---|
| **风险维度** | **时序** | **权柄** |
| 具体风险 | 漏做前置检查、步骤乱序、跳过安全闸口 | 越权断言学生属性、无证据写入画像、生成内容未过审 |
| 保证手段 | **图的边**（顺序边、条件路由、强制闸口） | **角色边界 + 能力面 + 证据纪律** |
| 失败表现 | "看起来专业但危险的错误" | "关于学生的断言不可回溯" |

- 项目 A 的典型事故是**过程性**的：禁忌症没查就算剂量。防这种错要靠**时间上的强制顺序**——只有边能做到。
- 项目 B 的典型事故是**声明性**的：系统断言"该生 MCA 供血区掌握良好"，但学生从没说过。防这种错靠**"谁有权说什么、需要什么证据"**——顺序无关，边管不了。需要的是**权柄结构**。

**同一个"用结构换确定性"原则，因为风险维度不同，长出了两种完全不同的结构。**

### 4.2 为什么只有项目 B 需要"仲裁智能体"

关键差别：**有没有外部真理源。**

- **项目 A 有真理源**：临床指南 + 规则引擎。多专家意见冲突时，可以**查表裁决**——`contraindication_check` 说活动性出血，那就是出血，不需要投票。所以 A 的多专家是"独立意见 → 交叉质询 → 主持人共识"，终点是一个**可被规则推翻**的结论。冲突由规则消解，不需要程序。
- **项目 B 没有真理源**：核心不确定性是"**这个学生是什么样**"。这件事没有可查询的权威——唯一权威是**学生自己的陈述与表现**。两位专家对同一句话可以都"很有道理"却得出相反结论，而这种歧义**原则上不可消解**。

所以在 B 里，冲突不能靠查表解决，只能靠一套**证据程序**来裁决：每条主张（Claim）标注证据（Evidence），逐条判 `ACCEPT / ACCEPT AS INFERRED / REJECT`。**这就是为什么只有 B 需要独立的仲裁角色，也只有 B 的仲裁 prompt 要专门警告"一致性不等于有证据"——因为没有真理源时，共识是最诱人但最不可靠的裁决者。**

| | 项目 A | 项目 B |
|---|---|---|
| 冲突的裁决者 | 外部规则引擎/指南 | 证据仲裁程序 |
| 共识的地位 | 参考（可被规则推翻） | **明确不可作为裁决依据** |
| 是否需要仲裁角色 | 不需要 | 必需 |

### 4.3 为什么项目 B 敢把"叫哪个专家"交给模型

这是两个项目最表面的形态差异，也最容易误读为"B 更激进"。实际恰恰相反：

> **项目 B 敢把专家调度交给模型，前提是它先把安全关键的部分搬出了调度路径。**

- **项目 A**：安全关键节点（`tool_use` 的 Level 顺序、`validate` 规则拦截、`compliance` 审计、`human_review`）**本身就在调度路径上**。谁先谁后是安全问题，所以调度**必须**留在代码里。
- **项目 B**：监督者（supervisor）只在一个**教学品质**层面的专家池里调度——少叫一次"学习激励智能体"是质量问题，不是安全问题。而 B 的安全关键部分（医学红线、画像写边界、意图门控）**被刻意留在监督者之外**，监督者碰不到。

所以 B 的"自主"是**被圈定过的自主**：

| 约束 | 机制 |
|---|---|
| 只能叫声明过的专家 | `expert_config.yaml` 的 `intent_expert_mapping`（每个意图一个固定菜单） |
| 只能做有限轮 | `SUPERVISOR_MAX_TOOL_ROUNDS`、`recursion_limit = 2*max_tool_rounds+8` |
| 只能用 5 个工具 | 工具白名单（`evidence_search` / `consult_experts` / `dispatch_agent` / `finalize_report` / `get_student_profile`） |
| 只对白名单意图生效 | `SUPERVISOR_INTENTS=tutor,profile,resource,assessment,learning_path` |
| 危险议题根本进不来 | 医学红线 + 输入守卫在监督者**之外** |

换句话说：**B 不是"把编排交给了模型"，而是"在静态菜单之上加了一层模型选择"。** 计划集合仍然可枚举（所以 SSE 契约依然稳定），只是从"固定顺序"变成了"声明式菜单 + 受限选择"。

对比项目 A 的 `intent` 路由也完全同理——A 也做意图门控：

| 意图 | 项目 A 的路径 | 项目 B 的路径 |
|---|---|---|
| 简单/无关 | `irrelevant → reject`；`knowledge → 单节点直答` | 非白名单意图 → 不走监督者 |
| 复杂 | `consultation → 完整三层流程` | 白名单意图 → 监督者调度专家 |

**两个项目都"该省则省"：简单问题走单跳，只有值得的请求才付多跳代价。** 项目 B 更进一步——tutor 模式默认关闭监督者（`SUPERVISOR_TUTOR_ENABLED=false`），因为单轮问答多跳只涨延迟不涨准确率。

### 4.4 不可逆性长在哪里，决定闸口设在哪里

两个项目都有强制闸口，但位置不同——因为**不可逆的东西不一样**。

| | 项目 A | 项目 B |
|---|---|---|
| 不可逆的是什么 | **动作**（rt-PA 剂量打出去就收不回） | **记忆**（错误的画像断言持久化，污染此后所有个性化） |
| 闸口位置 | 出口：报告生成前 `interrupt()` 强制医生复核 | 入口：画像写入前候选白名单 + 证据强制 + 合并策略 |
| 是否强制人工 | **是**（HITL 硬闸口，责任链） | 否（可回滚：可重新访谈、清空画像） |
| 循环预算 | 紧（反思 3 次、驳回 2 次） | 相对宽松（教学可试错） |

这个对照解释了一个容易被忽略的不对称：**项目 B 的单次回答是可逆的（学生可以再问），但项目 B 的记忆写入是不可逆的。** 所以 B 不需要"每份教学材料都请人签字"，却必须在"写学生画像"这一件事上极度克制。

> 项目 A 守的是**动作出口**，项目 B 守的是**记忆入口**。

### 4.5 共同底座：形态不同，工程纪律相同

两个项目在工程底座上高度一致，差别只在编排拓扑：

| 纪律 | 项目 A | 项目 B |
|---|---|---|
| 有界循环 | `max_reflection_count`、`HITL_MAX_REJECTS`、`query_rewrite` ≤2 | `max_reflection_count=1`、`SUPERVISOR_MAX_TOOL_ROUNDS`、`recursion_limit` |
| 意图门控 | `irrelevant` / `knowledge` / `consultation` | `SUPERVISOR_INTENTS` |
| 证据强制 | `R{轮}-Q{查询}-E{结果}` 编号 + `evidence_judge` | 5 态 `ev_status` + 证据引用 + 候选强制 `evidence` |
| 降级仍有闸口 | `fail` 仍走 `compliance` | 候选无证据即丢弃（不进合并） |
| 专家并行 | `asyncio.gather` | `asyncio.gather` |
| 结构化输出 + 回退 | `make_structured_runner` 双路径 + 规则兜底 | prompt 契约 + JSON 白名单归一 |
| 流式契约 | 固定 SSE 事件集 | 固定 SSE 事件集（`init/meta/node_start/thinking/...`） |
| 弱模型补偿 | 骨架 + 规则引擎补调 | 能力面 + 声明式菜单 + 上限 |

**两者都不是"把系统交给模型"，而是"用各自领域里最合适的那一维结构，把模型约束在安全范围内"。**

## 5. 选型判据（可复用清单）

以后遇到新场景，按这张表判断该做 workflow 还是 Agent：

| 判据 | 倾向 **workflow（边保证）** | 倾向 **多 Agent（权柄保证）** |
|---|---|---|
| 正确步骤能否枚举 | 能（指南/协议/流程） | 不能（教学设计、访谈策略） |
| 风险落在哪一维 | **时序**（漏步/乱序） | **权柄**（越权断言/写错） |
| 失败是否可逆 | 动作不可逆 → 强制人工闸口 | 记忆不可逆 → 写入路径隔离 |
| 有无外部真理源 | 有 → 规则/查表裁决 | 无 → 需要证据仲裁程序 |
| 是否需要人签字 | 强制（责任链） | 可选（可回滚） |
| 分支自由度 | 小（工具选择、检索策略） | 大（策略、内容、调度） |
| 模型能力 | 弱 → 骨架补 | 弱 → 契约 + 能力面补 |
| 前端是否要求步骤可知 | 是 | 是（用**声明式菜单**满足，而非开放规划） |

**注意最后一行**：两个项目都要求"步骤集合预先可知"（为了 SSE 契约与思考链渲染）。项目 B 用**声明式专家菜单**满足了这一点，所以 B 的监督者**不是开放式规划器**。这是 B 与"自主 Agent"的根本分界。

## 6. 答辩速答

**问：为什么临床项目用工作流，教育项目用多 Agent？**

> 因为两个项目的风险长在不同维度。临床项目的风险长在**时序**——漏做禁忌筛查、乱序、跳过安全闸口，这类错误只有**图的边**能防，所以骨架写死在 `clinical_graph.py`，连反思耗尽的降级路径都强制穿过 `compliance` 审计。教育项目的风险长在**权柄**——系统可能断言一条学生从没说过的事实，这跟步骤顺序无关，要靠**角色边界和证据纪律**来防，所以是监督者 + 专家注册表 + 证据仲裁。**同一个"用结构换确定性"原则，因为风险维度不同，长出了两种结构。**

**问：那为什么教育项目敢让模型自己调度专家？**

> 因为它先把安全关键的部分**搬出了调度路径**。监督者只在一个静态声明（`intent_expert_mapping`）的教学品质专家池里选，少叫一个专家是质量问题不是安全问题；医学红线、画像写边界、输入守卫都在监督者**之外**，它碰不到。而临床项目的安全节点（工具 Level 顺序、validate、compliance、HITL）**本身就在调度路径上**，所以调度必须留在代码里——**不是 B 更激进，是 B 先把危险挪走了才敢放手。**

**问：多 Agent 是不是效果更好？**

> 不是。10 个专家共用同一个基座模型，差别只有 prompt 和工具白名单，所以这套架构**不能也不该拿"效果更好"当卖点**。它成立的唯一前提是需求里有**互相冲突的角色目标**和**强制审计要求**——生成者不能当审核者，主张方不能当仲裁者。如果需求只是"把问题答好"，一个强模型加 RAG 是正确且更便宜的设计。

**一句话版本**：

> **临床项目用图的边守住"该做的一步不能少"；教育项目用角色的边界守住"不该说的话不能说"。两者都是把模型管起来，只是绑的方式不同。**
